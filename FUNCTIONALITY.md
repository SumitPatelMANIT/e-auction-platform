# E-Auction Management System - Architecture & Functionality

This document details the core modules of the E-Auction platform, how they function, and how they interact with one another across the frontend and backend.

## 1. System Roles
The system operates on Role-Based Access Control (RBAC), dividing functionality into three primary user journeys:
*   **ADMIN:** Oversees the platform. Creates auctions, manages the auction lifecycle, views system analytics, and handles support tickets.
*   **SELLER:** Adds inventory/items to the platform and tracks the status of their items (e.g., whether they have been auctioned off and at what price).
*   **BIDDER:** Searches catalogues, registers for auctions, participates in live real-time bidding, and manages their bid history.

## 2. Core Modules & Data Flow

### A. Authentication & Authorization Module
*   **How it works:** Users register and log in via the backend REST API (`/auth/register`, `/auth/login`). Passwords are encrypted using `bcryptjs`. Upon successful login, the server issues a JSON Web Token (JWT).
*   **Connection:** The frontend stores this JWT (usually in local storage/cookies) and attaches it to the HTTP Authorization header for all subsequent API requests. The backend uses middleware to verify the token and extract the user's ID and Role, ensuring Bidders cannot access Admin routes, for example.

### B. Inventory & Catalogue Management (Seller Module)
*   **How it works:** Sellers log into their dashboard (`InventoryDashboard.jsx`) to add new items. They provide titles, descriptions, base prices, and images.
*   **Connection:** The frontend sends a POST request to the backend `sellerController`. The backend saves the `Item` in the PostgreSQL database via Prisma, linking it to the `User` (Seller). These items are initially marked as "Pending" or "Unassigned".

### C. Auction Lifecycle Management (Admin Module)
*   **How it works:** Admins access the `AuctionLifecycle.jsx` dashboard. They select items provided by sellers and schedule an `Auction` (setting start times, end times, and minimum bid increments).
*   **Connection:** This creates an `Auction` record in the database linked to the `Item`. 
*   **Background Jobs:** The backend utilizes `node-cron` (`cronJobs.js`) to run background checks. It automatically changes auction statuses (e.g., from "Scheduled" to "Active", and "Active" to "Closed") based on the server's clock matching the auction's scheduled times.

### D. Live Bidding Engine (Real-Time Module)
*   **How it works:** This is the most critical module. When a Bidder joins an active auction page (`CatalogueSearch.jsx` / Live Auction View), the frontend establishes a WebSocket connection using `socket.io-client`.
*   **Connection:** 
    1. The bidder submits a bid.
    2. The frontend emits a `place_bid` socket event (or sends an HTTP request which then triggers a socket broadcast).
    3. The backend validates the bid: Is the auction active? Is the bid higher than the current highest bid + the minimum increment?
    4. If valid, the backend saves the `Bid` to PostgreSQL via Prisma.
    5. The backend's Socket.io server immediately broadcasts a `bid_update` event to *all* connected clients.
    6. The frontend's `AuctionContext.jsx` listens for this event and instantly updates the UI (Current Price, Highest Bidder) without requiring a page refresh.

### E. Post-Auction & Order Processing
*   **How it works:** When an auction reaches its `end_time`.
*   **Connection:**
    1. The `cronJob` detects the expired auction and marks it as "Closed".
    2. The system calculates the highest `Bid`.
    3. It automatically generates an `Order` record, linking the winning Bidder (`User`), the `Auction`, and the `final_price`.
    4. A `Notification` is generated alerting the Bidder that they won.
    5. The Bidder can then view their won items in the `MyBidsDashboard.jsx` and proceed to simulated payments (`Payment` model).

### F. Notifications & Ticketing System
*   **Notifications:** Generated by system events (e.g., "You have been outbid!", "Auction Won"). They are stored in the `Notification` table and can be pushed in real-time via WebSockets to the user's navbar.
*   **Ticketing:** Users can submit support requests (`Ticket`). Admins view these in their dashboard and can update their status to "Resolved".

## 3. Technology Integration Summary

*   **Frontend (React) ↔ Backend (Express):** Communicate primarily via REST APIs (fetching historical data, submitting forms) using `fetch` or `axios`.
*   **Frontend (React) ↔ Backend (Socket.io):** Communicate via WebSockets for low-latency, real-time data specifically for live bidding and timer synchronization.
*   **Backend ↔ Database (PostgreSQL):** Communicate securely via the Prisma ORM, which ensures type-safety and prevents SQL injection.
*   **Backend Internal (Node-Cron):** Operates independently of user requests, periodically polling the database to trigger state changes in the auction lifecycle.
